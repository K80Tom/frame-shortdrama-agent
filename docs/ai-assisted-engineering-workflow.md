# Lyra AI 辅助工程化流水线工作指南

> **核心哲学**：
> 辅助编码的效率不取决于模型有多聪明，而取决于软件工程基础设施有多扎实。  
> $$\text{AI 交付效率} \approx \text{模型能力} \times (\text{软件工程能力} + \text{架构能力} + \text{基础设施能力})$$  
> **在概率的不确定中，用经典计算机科学（DDD、依赖倒置、测试金字塔）建立交付的确定性。**

---

## 1. 为什么拒绝原始的 Vibe Coding？

在小型 Demo 中，“靠感觉对话、不看代码”可以迅速产出原型。但在 Lyra 这种中大型多包协作系统中：
* **无约束的生成会导致架构坍塌**：AI 是局部专家、全局盲人。缺乏边界时，它会随意 cross-import，把数据库依赖写进纯逻辑包，导致模块严重耦合。
* **海量代码让人力审查破产**：AI 产出的代码量极大，逐行 Code Review 的成本远超自己重写。
* **没有测试的代码不可控**：一旦需求变动，AI 修复 A 会破坏 B，陷入死循环。

我们的解法不是等待模型进化，而是**将工程纪律封装为自动化流水线**：
你负责 **Vibe（意图、边界与体验）**，基建负责 **Code（实现、自愈与回归）**。

## 2. 标准 4 拍交付流水线 (The 4-Beat Pipeline)

所有功能交付必须从一个标准清晰的 [AI Task Spec](../.github/ISSUE_TEMPLATE/5_ai_spec.yml) 开始，并按以下 4 拍节奏推进：

```text
[第 1 拍：契约先行]
  └─ 人类定边界与契约 ──> AI 修改 packages/shared ──> 人类 30 秒快速审定契约
         │
[第 2 拍：红灯测试]
  └─ AI 将 Spec 验收场景转写为自动化测试 (Unit / Integration) ──> 运行必红 (失败)
         │
[第 3 拍：黑盒自愈]
  └─ AI 编写实现代码 ──> 自启动/调测试 ──> 捕获报错并自我修复 ──> 测试全绿
         │
[第 4 拍：体验质检与 PR]
  └─ 本地启动验证 (CLI / Web) ──> 人类仅打磨交互体验与美学 ──> 按规范建 PR
```

### 第 1 拍：契约先行 (Contract First)
* **原则**：契约没定死，严禁写业务逻辑。
* **执行**：
  1. 在 `packages/shared` 中定义数据结构、领域对象和请求/响应接口。
  2. 运行 `npm --prefix packages/shared run build` 确保类型无语法错误。
  3. **人类介入**：仅花 20~30 秒审视接口命名、可选字段与层级关系。这一步锁死 AI 的活动牢笼。

### 第 2 拍：红灯测试 (Spec as Tests)
* **原则**：能写出单测的代码，架构必然可测且解耦。
* **执行**：
  1. 提示 AI：“根据 Spec 中的验收场景，在目标包的 `test/` 下补充单测或集成测试桩，不要写实现代码。”
  2. 运行测试：`npm --prefix <target_package> test`。
  3. **验证结果**：所有新增用例必须**红灯（报错/失败）**，证明测试用例是真实有效的，而非无意义的空断言。

### 第 3 拍：黑盒自愈 (Self-Healing Loop)
* **原则**：让 AI 做自己的测试与审查，彻底解放人类双手。
* **执行**：
  1. 提示 AI：“编写具体实现代码，自行运行测试，分析堆栈报错并循环修复，直到所有测试变绿。”
  2. **跨包约束硬阻断**：AI 在编写过程中严禁越权（如在 `agent` 包直连数据库）；一旦违背，单测或构建检查直接失败。
  3. **自愈完成标志**：本地测试全绿，且 `npm run build` 全量通过。

### 第 4 拍：体验质检与 PR (Human Touch & Delivery)
* **原则**：机器保正确，人类保体验。
* **执行**：
  1. 启动服务：`npm run dev` 或 `npm run dev:web`。
  2. **人类感官验收**：
     - Web 端：视觉层次、排版间距、加载态动效与异常提示是否舒服。
     - CLI 端：终端高亮、格式化排版、日志清晰度是否易读。
  3. **合入纪律（严格遵守 AGENTS.md）**：
     - 在独立 worktree 中验证无误；
     - 运行全量门禁：`npm test`；
     - 发起 PR：`gh pr create --base dev`，填写完整 PR 模板。

## 3. Monorepo 跨包硬约束核对表

在流水线执行期间，必须严格遵守各包边界：

| 代码包 | 核心职责 | 绝对红线 (严禁行为) |
| :--- | :--- | :--- |
| `packages/shared` | 领域模型、公共契约、通用类型 | 严禁引入任何外部服务实现或 Node 后端依赖 |
| `packages/agent` | AI 状态机、工作区编排、只读提示词与工具 | **严禁 import 数据库驱动、严禁读取密钥环境变量、严禁监听端口** |
| `packages/main` | 数据主权、PostgreSQL 持久化、NestJS 服务、付费模型调用 | 必须严格执行估价/确认门禁；严禁向前端泄漏未脱敏的凭证 |
| `packages/web` | React 工作台前端界面 | 仅调用 `main` 的 HTTP API；共享类型严格来自 `@lyra/shared` |
| `packages/cli` | 开发者/自动化命令行工具 | `run create` 仅生成计划，`run submit` 才能触发执行 |

## 4. 常用流水线指令速查

```sh
# 1. 契约构建验证
npm --prefix packages/shared run build

# 2. 独立包测试自愈循环（推荐针对修改包快速执行）
npm --prefix packages/agent test
npm --prefix packages/main test
npm --prefix packages/web test

# 3. 真实数据库集成测试（需已执行 npm run db:up && npm run db:migrate）
npm --prefix packages/main run test:db

# 4. 全库回归验证（提 PR 前必跑）
npm run build
npm test
```

## 5. 团队协作心智

1. **从“写代码的打字员”转变为“系统架构师与导演”**：把 80% 的精力放在业务意图、边界设计（DDD）和测试场景推演上。
2. **测试不再是负担，而是生产力杠杆**：在 AI 时代，代码生产边际成本为零，测试代码是唯一的安全气囊。
3. **遇到 Bug 先补测试，再让 AI 修逻辑**：永远不要直接在自然语言里“吵架式 Debug”，而是把复现 Bug 写成一个挂掉的测试用例，交给流水线自愈。
