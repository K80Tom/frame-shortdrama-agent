# P0.3：事实候选与 PlanRevision

更新日期：2026-10-01。

P0.3 建立“模型产物不能直接成为正式计划”的程序边界。它接收一份 `extractFacts` 候选，校验后保存为不可变的 `Candidate PlanRevision`。P0.3 本身不启动 StageExecutor 或模型调用；后续 P0.4 已将这个领域入口用于可留痕的假适配器执行。保存成功仍不表示候选已被采用。

## 已实现链路

```text
已保存的 draft Run / extractFacts Task
→ 候选事实请求
→ TypeBox / Ajv 结构校验
→ 原文与领域校验
→ 临时 ID 映射为程序生成的稳定 ID
→ PostgreSQL plan_revisions
→ 读取候选，等待未来的检查与采用
```

候选内容包含梗概、人物、地点、道具、场次和原文对白。事实提取阶段的 `shots`、`assetRequirements`、`manualLocks` 固定为空；分镜设计、资产需求与人工修改保护在后续阶段加入。

## 程序校验

- 所有 `SourceRef` 必须绑定 Run 固定的 `ScriptVersion`；`start/end` 按 Unicode 码点解释，`quote` 必须与原文精确相等。
- 候选只允许 `origin=source`；P0.3 尚无 Answer，`answerIds` 必须为空。
- 模型侧临时 ID 在单份候选内必须唯一；程序为人物、地点、道具、场次、对白和计划版本生成稳定 ID，并一次性重映射引用。
- 场次 `order` 从 1 开始、连续且唯一；地点和人物引用必须存在。
- 对白必须属于有效场次，已确认说话人必须在该场人物中并具有依据；对白正文必须位于场次原文范围内，并按场次和原文顺序排列。
- 任一校验失败时整份候选不写入数据库，返回 `422 CANDIDATE_PLAN_INVALID`。

这些规则验证结构、引用和确定性关联，不判断梗概是否完整、人物是否漏提、场次语义是否准确。语义复核和 Issue 记录仍未实现。

## 保存与采用边界

`migrations/002_candidate_plan_revisions.sql` 创建 `plan_revisions`，并给 `projects` 增加可空的 `active_plan_revision_id`。当前写入记录固定为：

- `status=candidate`
- `createdBy=agent`
- `reason=extract`
- `validatorVersion=extract-facts-validator/1`
- `parentRevisionId=null`
- `rebasedFromRevisionId=null`

P0.3 没有采用接口，不更新 `Project.activePlanRevisionId`。同一个 Run 可以保留多份候选，后续 Attempt/Check 才负责说明候选来源、检查结果与采用资格。

## 本地 API

所有接口沿用本机 Host、Origin 和 `X-Shortdrama-Call: 1` 保护。

| 方法 | 路径 | 作用 |
|---|---|---|
| `POST` | `/api/breakdown-runs/:runId/candidate-plan-revisions` | 校验并保存事实候选。 |
| `GET` | `/api/breakdown-runs/:runId/candidate-plan-revisions` | 按创建顺序读取该 Run 的候选。 |
| `GET` | `/api/plan-revisions/:planRevisionId` | 读取一份候选快照。 |

该 POST 是 StageExecutor 后续调用的领域入口，目前不会自行调用模型，也不会改变 Run/Task 状态。
