# P0.4：受控的事实提取阶段

更新日期：2026-10-01。

P0.4 把 P0.1 的原文证据与 P0.3 的候选计划串成一次可追踪的 `extractFacts` 执行。它建立的是阶段执行边界，不是完整的短剧 Agent。当前只在离线测试和 PostgreSQL 集成测试中使用假模型适配器，没有公开“开始拆解” HTTP 接口，不会产生模型费用。

## 已实现链路

```text
draft Run / pending extractFacts Task
→ 读取已固定的 ScriptVersion 与 inputManifest
→ Prompt Chunk 和任务局部 Evidence Alias
→ Run=running，Task=running，创建 Attempt
→ 提交前创建 ModelCall（prepared → submitted）
→ 假模型适配器返回仅含 alias 的候选
→ chunkId + alias 还原为 canonical SourceRef
→ P0.3 结构、原文和关系校验
→ 保存绑定 Attempt 的 Candidate PlanRevision
→ Attempt=succeeded，Task=waitingHuman，Run=waiting
```

`SingleModelCallExtractFactsExecutor` 定义阶段约定，`StageModelAdapter` 隔离具体模型。以后接 Pi Agent Core 时，替换 Executor／Adapter 层，不让 Pi 直接写数据库、修改状态或采用计划。

## 证据边界

- alias 只在当前 Prompt Chunk 内有效，因此模型返回 `{ chunkId, alias }`；单独的 `E001` 不能全局定位。
- `E...` 是 primary 证据，可支撑输出；`C...` 只是相邻上下文，不能单独成为事实依据。
- 对白必须引用 primary alias，并提供在该证据内精确且唯一出现的对白文本。程序按 Unicode 码点派生更窄的 `SourceRef`。
- 未知 alias、只用 context、不唯一对白或伪造 quote 都在写入前失败。

## 留痕与失败关闭

`migrations/003_extract_facts_execution.sql` 新增 `breakdown_attempts` 和 `model_calls`，并让 `plan_revisions.attempt_id` 可追溯来源。模型调用保存内部 `operationKey`、请求摘要、供应商请求 ID 和用量，不保存原始供应商响应。

模型调用成功但候选校验失败时，`ModelCall=succeeded` 而 `Attempt/Task/Run=failed`；这能区分“调用失败”和“产物不合格”。适配器异常只保存已清洗的错误码和说明，不落库原始异常内容。`maxModelCalls` 在调用适配器前强制执行。

## 当前边界

- 只支持 draft 中的单次首次 Attempt；自动重试、租约、进程恢复和 `unknown` 对账尚未实现。
- 当前上限校验等价于“单任务唯一 Attempt 的调用总数”；增加重试前要改为跨 Attempt 统计。
- Candidate 写入与 Attempt 完成为两个短事务；进程在两者之间中断时的恢复规则尚未实现。
- 未实现 CostEntry，不可将当前记录称为正式费用账本。
- 未接 Pi Agent Core、真实模型、语义质检、Issue／Check／Adoption、分镜生成和网页操作。
