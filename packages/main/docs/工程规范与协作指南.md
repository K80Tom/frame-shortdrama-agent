# Lyra 工程治理与协作规范 (v1.0)

> 本规范落实 Issue #70、#71、#72 的治理要求，为仓库的分支流向、权限控制、Issue 模板与代码合并提供单一权威真源。

---

## 一、 分支策略（Trunk-Based with Dev Staging）

仓库采用双主干开发与发布模型：

```text
    feature/fix 分支 (从 origin/dev 切出)
         │
         │ (PR + 必须真人 Review + CI 通过)
         ▼
     [ dev 分支 ]  ← 每日主集成分支 (保持随时可构建测试)
         │
         │ (版本发布 PR：dev -> main，严格审批)
         ▼
     [ main 分支 ] ← 生产就绪发布分支 (受强保护，严禁直推)
```

### 1. 分支职责划分

| 分支 | 角色定位 | 准入规则 |
| --- | --- | --- |
| `main` | **生产就绪发布分支** | 受保护分支。只接受来自 `dev` 的发布 PR；禁止直接推送，禁止普通 feature/fix 分支合入。 |
| `dev` | **日常主集成分支** | 受保护分支。所有日常新特性（`feat/*`）、缺陷修复（`fix/*`）、重构（`refactor/*`）的目标分支。 |
| `feat/*`, `fix/*` | **短生命周期特性/修复分支** | 从最新 `origin/dev` 切出，建议存活时间 ≤ 2 天，单个 PR 聚焦解决一件事。 |

### 2. Worktree 开发隔离规则

为防止多任务并行时的上下文污染、端口冲突与未暂存代码泄漏，必须强制采用 Git Worktree：
```sh
# 1. 抓取最新远程代码
git fetch origin

# 2. 从最新 origin/dev 创建独立短分支并建立工作区
git worktree add ../lyra-<topic> -b feat/<topic> origin/dev

# 3. 进入工作区进行开发、独立安装依赖与构建验证
cd ../lyra-<topic>
npm run build
npm test

# 4. 提交并通过 PR 合入 dev，合入完成后清理工作区
git worktree remove ../lyra-<topic>
git branch -d feat/<topic>
```

## 二、 CI 门禁与合并安全原则（禁止机器人自动合并）

根据 Issue #71 安全审计要求，彻底废除 GitHub Actions 具有写权限的 Autopilot 自动合并机制。

1. **权限最小化**：
   GitHub Actions 顶层权限严格设定为只读：`permissions: contents: read`。禁止授予写入或合并权限。
2. **目标分支合规门禁 (`branch-guard`)**：
   CI 第一步检查 PR 目标分支：若普通 PR 误向 `main` 提交，门禁直接报错红灯阻断，提示开发者修改目标为 `dev`。
3. **真人审批（Human Approval）原则**：
   - 任何合入 `dev` 或 `main` 的 PR，必须至少获得 **1 名非 PR 作者的团队成员真人 Approve**。
   - 机器人或 AI 辅助 Review 仅提供只读建议（输出至 Step Summary 和评论），不能充当真人审批。
   - 当 PR 推送了新 Commit 后，旧的审批标记自动作废，必须重新核验。

## 三、 Issue 与 PR 规范

### 1. Issue 模板与分类

所有需求与缺陷必须通过 GitHub Issue 模板发起：
- **Epic（史诗）**：包含整体愿景、子 Issue 清单、全局非目标与 DoD。
- **Feature（特性）**：包含业务价值、改动范围、验收标准 Checklist、潜在风险（付费/迁移/安全）。
- **Bug（缺陷）**：包含复现步骤、预期 vs 实际、关联日志（严禁泄露密钥）。
- **Refactor（重构）**：包含重构动机、受影响包、向后兼容性保证。

### 2. 标签体系 (Labels)

- **类型 (`type/*`)**：`type/epic`、`type/feat`、`type/fix`、`type/chore`、`type/docs`、`type/refactor`、`type/test`
- **业务模块 (`area/*`)**：`area/script`、`area/novel`、`area/audio`、`area/previs`、`area/review`、`area/runtime`、`area/data`、`area/eval`、`area/security`
- **优先级 (`priority/*`)**：
  - `priority/P0`：系统阻塞、资损风险、CI 安全漏洞、破坏性故障
  - `priority/P1`：关键路径功能、本轮核心迭代目标
  - `priority/P2`：演进增强、非阻塞体验优化
- **风险标记 (`risk/*`)**：
  - `risk/paid-model`：涉及外部付费模型调用，必须核对预算预留与确认卡
  - `risk/migration`：包含 PostgreSQL 结构迁移
  - `risk/security`：涉及鉴权、SSRF、文件下载或外网调用
